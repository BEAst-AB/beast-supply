BEASt Supply Release Process

1. Create new branch from Main (naming convention from POACC is now 2026-Q2-DEV-v4.0.7 i.e. Year-Quarter-Type-Version). Add a new release notes page and update the release in the header on the main page.

2. Create an individual issue branch from the Dev branch in case it is a change that is substantial.

3. Develop the issue and add it to the new release notes.

4. Commit the change to the branch and if the branch is an individual branch - create a pull request to the DEV branch - accept the pull request or ask for a review depending on the complexity of the solution.

5. Adjust the build.sh and sync repo.sh to import from upcoming branches (make sure they are updated with the latest, otherwise use MR-branches instead)

6.  When development is done, do qa and the dev-team lead create a new branch from DEV (named the same as the Dev branch except MEMBER_REVIEW instead of DEV)

7. Let the memeber review have its process

8. Get the member comments and adjust accordingly 

9. Create a pull request from the memer review release to the release and on publication date: accept the pull request.
adjust the import branches to import from the corresponding released branches in POACC and Logistics (i.e. change to "upcoming" if you are still using MR)

10. on mandatory date - check that the main and master branches from POACC and Logistics are updated. Create a pull request towards main and ask or it to be reviewed by another team member and accepted.




Timeline towards the rest of the branches.
Branches to use:

POACC:
Dev branch - entire dev cycle
Release candidate - during review
released branch (2025-Q4 for example) from publication until mandatory
main - from mandatory date

Logistics:
Same as Poacc but normally with a little delay and they are using "upcoming" in github.
